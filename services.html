How we work with enterprise teams

From a bounded pilot to a clean handover.

  1. Step 1

    Start with a bounded pilot

    We agree the success measures, the data in scope and the autonomy level before work begins.

  2. Step 2

    Prove it on safe data first

    Pilots run on synthetic or sanitised data until your security and risk teams have reviewed the controls.

  3. Step 3

    Transfer knowledge as we build

    We work alongside your engineers and hand over documentation, evaluation suites, tests and runbooks, so the system does not depend on us.

  4. Step 4

    Plan the exit at the start

    Ownership of code and IP, handover and transition responsibilities are agreed in the contract, not after delivery.

How we deliver

  • Autonomy is set to match the risk

    Each workflow is assigned one of four levels: observe, advise, act with approval, or act autonomously. Higher-risk workflows get tighter controls rather than one blanket policy.

    Seen in

    • Financial investigation
    • Operations agents
    • Conversational commerce

  • Controls are enforced in code

    Spend limits, approved-vendor lists, read-only data access and approval gates are applied by deterministic logic before any action runs. If one component fails, deterministic fallbacks, automatic re-weighting and cached responses keep the service running.

    Seen in

    • Financial investigation
    • Operations agents
    • Conversational commerce
    • Phishing detection

  • Every output is traceable

    Findings cite their evidence. Diagnoses cite the rule that produced them.

    Seen in

    • Financial investigation
    • Drug-interaction analysis
    • Visual inspection

  • Results are reported candidly

    Where a simple rule outperformed a learned model, or a headline score was partly circular, we say so.

    Seen in

    • Response-planning simulators
    • Drug-likeness review

  • Systems are built to be owned

    Architecture is documented, evaluation suites and tests ship with the code, model providers can be swapped, and benchmark scripts let your team reproduce every figure. The aim is that your engineers can run and extend each system without us.

    Seen in

    • Financial investigation
    • Operations agents
    • Price intelligence
    • Phishing detection

  • Evaluation precedes data sharing

    Demonstrations run on synthetic or public data, so behaviour can be assessed before any sensitive data is exposed.

    Seen in

    • Financial investigation

    • Churn prediction

Security by design

Our agent work is designed against the risks in the OWASP Top 10 for Agentic Applications (2026). The controls below are built into the projects listed. They support your own security review and do not replace it.

  • ASI01

    Agent goal hijack

    Orchestration and limits sit in code rather than in the prompt, so instructions hidden in a document or message cannot change the limits the agent works within.

    • Financial investigation
    • Operations agents
  • ASI02

    Tool misuse and exploitation

    Tools are narrow and guarded: read-only database access, spend limits, approved-vendor lists and tolerances.

    • Financial investigation
    • Operations agents
  • ASI03

    Identity and privilege abuse

    Permission policy is explicit, and consequential actions pass an approval gate before they run.

    • Financial investigation
    • Operations agents
  • ASI08

    Cascading failures

    Writes are idempotent and verified by read-back. Run state persists, and work replays safely after a forced shutdown.

    • Operations agents
